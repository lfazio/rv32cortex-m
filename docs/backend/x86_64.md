# The x86-64 backend

`src/backend/x86_64/` — and it exists for **coverage, not speed**.

The Thumb-2 backend's lowering cannot be exercised by any host suite:
every JIT bug this project has found there needed a board, a flash cycle
and a UART, and three of them were live for months first. With an x86-64
emitter, the architecture suite and riscv-tests run against *translated*
code on a host, and `ctest` runs the guests a second time under `--jit`.

```sh
./build/host/emu-host --jit --quiet build/host/guest/isatest.bin
EMU_EXTRA_ARGS=--jit ./scripts/run-arch-test.sh
EMU_HOST=<wrapper adding --jit> ./scripts/run-riscv-tests.sh
```

Like the Thumb-2 one it is a lowering of the shared IR and nothing else:
`encode.c` spells instructions, `ir_lower.c` turns an IR block into a
host block, and neither knows its guest. All four frontends have a JIT
here — RV32, G4MH, ARMv7-M and PowerPC — from one macro in
`src/emu/emu_ir_jit.c`.

---

## Read the stats line

A backend that declines everything and falls back passes every test while
proving nothing, so the runner prints what was translated, entered and
interpreted. The first run of this backend said `interp 7807` of 8527 —
92% interpreted, because compressed encodings were skipped and `isatest`
locks a PMP entry early, after which everything went to the interpreter.
Today `isatest --jit` interprets 436 of 45,799.

The same line is where an *unhelpful* lowering shows, and it has to be
read per frontend: PowerPC's translator routed 165 of 1,332 instructions
to its helper for a while, with every test passing, because
`emu_ir_can_lower` here answers **false by default** and did not name the
byte swaps, the leading-zero count or the high multiplies it does lower.
An answer that defaults to "no" is a silent decline. (Thumb-2's defaults
to "yes", which is a promise it once broke for the rotates.)

## Registers and the frame

`rbx` is the cpu pointer and `rbp` the retired count; `eax`, `ecx` and
`edx` are scratch; every IR value has a home in the frame at `rsp`, and
`r12`–`r15` — the four callee-saved registers System V leaves free — are
handed out on top of that by `emu_ir_regalloc`.

Four is most of what there is to get, and the fourth is nearly free to
give up. Sweeping over RV32 CoreMark, emitted code size:

| registers | bytes |
|---|---|
| 0 | 173,828 |
| 1 | 167,492 |
| 2 | 164,120 |
| 3 | 162,836 |
| 4 | 161,932 |

The first register is 3.6% and the fourth is 0.6%. Live sets in these
blocks are small, which is what 4.12 guest instructions a block should
predict — so do not go looking for more registers before looking for
longer blocks. (The absolute figures predate later lowerings; the shape
is the result.)

## Where the bytes go

Emitted bytes per IR operation, summed over every block translated, RV32
CoreMark — 158,664 bytes for 2,725 guest instructions, **58 bytes each**:

| operation | count | bytes | share | each |
|---|---|---|---|---|
| `LOAD` | 458 | 45,732 | 28.8% | 100 |
| `STORE` | 290 | 30,241 | 19.1% | 104 |
| `EXIT_IF` | 416 | 17,804 | 11.2% | 43 |
| `GET` | 1,891 | 15,094 | 9.5% | 8 |
| `PUT` | 1,852 | 13,855 | 8.7% | 7.5 |
| `SETPC` | 858 | 9,438 | 5.9% | 11 |
| `RETIRE` | 2,725 | 8,175 | 5.2% | 3 |
| `EXIT` | 238 | 6,353 | 4.0% | 27 |

**A memory access is a hundred bytes**, and loads and stores are half of
everything emitted: the inlined window test, the access, and the
out-of-line call to the checked accessor with its trap exit. That is the
term to attack before any other, on either host.

`SETPC` was 3,235 operations and 19.3% before the optimiser learned that
a pc write nothing observes is dead (see
[../jit/README.md](../jit/README.md)); it was found by this histogram.
PowerPC's CoreMark is 70 bytes per guest instruction on the same
measure, the difference being condition-register arithmetic: 1,934
`SETCC` and some 8,000 shifts, masks and ORs that RV32 has no use for.

The instrument is thirty lines around the call to `lower_one` and is not
in the tree.

## Sizing

The microcontroller's JIT sizes are wrong for a host, in the direction
that hides bugs: 256 blocks and a few tens of kilobytes made CoreMark
flush 19 times a run, and constant retranslation is exactly what would
mask a translator bug behind a fresh translation. Here it is 65,536
blocks, a 32 MB buffer and an 8 KB reserve.

**Which means a host never meets what a small cache does.** No block
here reaches the reserve, so a translation never overflows the buffer,
so the path that compacts *because* of an overflow had never run on a
host — and it was broken, in this backend's link hook as much as in
Thumb-2's. See "Committed code is not emission" in
[thumb2.md](thumb2.md). The board's conditions can be had on a host by
defining four macros through `CMAKE_C_FLAGS` — `EMU_JIT_BLOCK_RESERVE`
512, `EMU_HOST_JIT_CODE_BYTES` 32768, `EMU_JIT_MAX_BLOCKS` and
`EMU_JIT_HASH_SIZE` 256 — and a runner built that way segfaulted on the
first guest large enough. `test_overflow_compaction_unlinks` is the same
situation with a stub translator, in every build.

## Encoding hazards

- **A hand-encoded ModRM will not tell you the register did not fit.**
  `ld_slot`/`st_slot` built the byte as `0x84 | (reg << 3)` for the three
  scratch registers they were written for. Handed r12, the fourth bit
  fell off the top of the three-bit field and `mov r12d, [rsp+n]`
  assembled as `mov esp, [rsp+n]` — the block loaded a guest value into
  its own stack pointer and did not fault until the return. Encoders that
  take a register parameter belong in `encode.c`, where the REX and
  high-register logic is written once.
- **System V wants rsp 16-byte aligned at a `call`.** Entry leaves it 8
  past, two pushes bring it back to 8, so the block prologue needs one
  more 8. Getting it wrong does not fault in the emitted code — it faults
  inside whatever libc routine a helper eventually reaches that uses an
  aligned SSE store.
- **Materialise the flags once.** `emit_setf` folded each `setcc` into an
  accumulator with `shl` and `or`, both of which write ZF/SF/CF/OF, so
  only the first flag saw real flags. `seto` plus `lahf` snapshots them
  before anything clobbers them. RV32 never emits this, so only a flag
  machine could reach it.
- **`x86_patch_rel32` is for the block being emitted.** It declines
  while the buffer has overflowed, because its slot may be past the end.
  A jump in committed code — a chained exit, a retired block's entry —
  is `x86_write_rel32`, which does not ask.

## What it declines

Nothing about the guest. Whether a block may be translated at all, and
whether its memory accesses may be inlined, is the frontend's decision:
RV32 translates under PMP and paging, with every access going through
the checked accessors and the inlined window withdrawn, and keeps blocks
honest through its context and generation keys
([../jit/staleness.md](../jit/staleness.md)). Only Sdtrig still sends
everything to the interpreter.

This backend once carried that gate itself, declining PMP and paging
because it implemented neither, and copying the gate to Thumb-2 cost
that backend most of its coverage. The decision moved to where the
knowledge is.

## The differential checker

`-DEMU_JIT_DIFF=ON` runs `emu_ir_interp` beside each freshly compiled
block and compares the guest state. It works on any platform — the
report goes through the console — and it has two blind spots worth
knowing before trusting its silence:

- `ir_diff_ref` runs the reference on the **optimised** IR, so when the
  defect is in an IR pass the reference and the compiled code are wrong
  identically and agree perfectly. A checker that compares two consumers
  of a bad input validates the consumers, not the input.
- It declines any block holding a store or a helper call, which is most
  of an architecture test — so "declined everything" and "agreed with
  everything" are the same silence. `diff_checked`/`diff_declined` are
  in the stats line for exactly that reason.

And it compares values, so it cannot see a defect in the *framework* —
a block that is correct and is then moved wrongly agrees with its
reference every time it is checked.
